最小收藏 API：三层各做一件事

目标不是记住 Spring 注解，而是让一条 HTTP 请求穿过正确的边界。先把接口和规则定清楚，AI 才能可靠地帮你补实现。

先定契约

用户点击收藏：

POST /api/wallpapers/42/favorite

201 Created
{ "id": 7, "wallpaperId": 42 }

这里刻意没有 userId：真实应用应从登录后的认证上下文取得当前用户，而不是让浏览器声明“我是谁”。

再写调用骨架

@RestController
@RequestMapping("/api/wallpapers")
class FavoriteController {
  private final FavoriteService favoriteService;

  @PostMapping("/{wallpaperId}/favorite")
  ResponseEntity<FavoriteResponse> favorite(
      @PathVariable Long wallpaperId,
      @AuthenticationPrincipal AppUser user) {
    FavoriteResponse result = favoriteService.favorite(user.id(), wallpaperId);
    return ResponseEntity.status(HttpStatus.CREATED).body(result);
  }
}

Controller 只处理 HTTP：路径参数、身份、状态码和响应。

@Service
class FavoriteService {
  private final WallpaperRepository wallpapers;
  private final FavoriteRepository favorites;

  @Transactional
  FavoriteResponse favorite(Long userId, Long wallpaperId) {
    wallpapers.getByIdOrThrow(wallpaperId);
    Favorite saved = favorites.save(new Favorite(userId, wallpaperId));
    return FavoriteResponse.from(saved);
  }
}

Service 处理业务流程：壁纸是否存在、重复收藏的产品规则、以及操作是否作为一个事务完成。

interface FavoriteRepository {
  Favorite save(Favorite favorite);
}

Repository 只表示持久化能力。实际项目中，唯一约束由数据库保证，Service 决定遇到重复时返回已有资源还是 409 Conflict。

AI 的正确用法：让它按这个契约生成 DTO、实体和测试草稿；你负责检查它是否把 HTTP、业务规则和持久化细节混在同一个类里。

检索练习

“壁纸不存在时不能创建收藏”这条判断首先应出现在哪里？

你的架构决定

重复点击收藏时，你会选择哪种 API 语义：返回已有收藏，还是返回 409 Conflict？用一句话说明理由。没有唯一正确答案，但必须让前端和后端使用同一约定。
