# 思维指南

> **目的**：扩展思考面，捕捉你可能没想到的东西。

---

## 为什么需要思维指南？

**大多数 bug 和技术债来自"没想到"**，而不是能力不足：

- 没想到层边界会发生什么 → 跨层 bug
- 没想到代码模式在重复 → 复制粘贴泛滥
- 没想到边界情况 → 运行时报错
- 没想到未来的维护者 → 不可读的代码

这些指南帮你在**写码前问出正确的问题**。

## 速查：思考触发条件

### 何时思考跨层问题

- [ ] 功能触及 3+ 层（API、Service、Component、Database）
- [ ] 数据格式在层间变化
- [ ] 多个消费者需要同一份数据
- [ ] 你不确定某段逻辑该放哪
- [ ] 你在新增事件类型、JSONL 记录、RPC 载荷或配置字段
- [ ] UI / 命令代码开始直接 cast 原始载荷字段

→ 阅读[跨层思维指南](./cross-layer-thinking-guide.md)

### 何时思考代码复用

- [ ] 你在写与已有代码相似的代码
- [ ] 同一模式重复出现 3+ 次
- [ ] 你在往多处加同一个新字段
- [ ] **你在修改任何常量或配置**
- [ ] **你在新建工具/辅助函数** ← 先搜索！
- [ ] 两个文件用本地 cast 读同一个无类型载荷字段
- [ ] 多个分支从 `kind` / `action` 更新同一份派生状态

→ 阅读[代码复用思维指南](./code-reuse-thinking-guide.md)

### 校验 AI 交叉评审结论时

- [ ] 评审者声称"用户输入可能恶意" → 核实真实数据来源（内部清单？用户配置？外部 API？）
- [ ] 评审者标记"缺少校验" → 数据是否来自可信内部来源？
- [ ] 评审者说"行为变了" → 读代码注释——是不是有意设计？
- [ ] 评审者在测试里发现"bug" → 心理上删掉被测功能——测试还能过吗？能过 → 恒真测试

**AI 评审者常见误报模式**：
1. **信任边界混淆**：把内部数据（打包的 JSON 清单）当成不可信外部输入
2. **无视设计注释**：把代码注释里写明的有意行为标成 bug
3. **变量误读**：没有把变量追溯到真实定义（如按路径索引 vs 按名称索引的 Map）

**校验规则**：每条 CRITICAL/WARNING 结论在排优先级前必须对照真实代码核实。给 AI 评审预留约 35% 的误报率。

## 修改前规则（关键）

> **改任何值之前，永远先搜索！**

```bash
# 搜索你要改的值
grep -r "value_to_change" .
```

这一个习惯能防止大部分"忘了同步改 X"类 bug。
